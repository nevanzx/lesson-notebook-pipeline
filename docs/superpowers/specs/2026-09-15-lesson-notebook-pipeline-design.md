# Interactive Lesson Notebook v2.0 — Component Pipeline Design

Date: 2026-09-15
Status: Approved by user in brainstorming session (pick+tune themes, parts-folder builder, registry + promotion gate, business-focused pack set)

## 1. Problem

`interactive-lesson-notebook` v1.9 makes the model re-emit ~2,300 lines of HTML/CSS/JS per
lesson, of which ~60–70% is unchanged boilerplate (shell, component code, print rules,
parsers). Costs: high output tokens, slow builds, mid-file truncation risk, and recurring
regressions of documented pitfalls (§5.4) that get re-typed wrong each time.

Goal: standardize the mechanics into shipped assets so the model outputs **only lesson
content**, while keeping the skill's core philosophy — every notebook still looks like its
own world — intact.

## 2. Locked decisions

| # | Decision | Choice |
|---|---|---|
| 1 | Theme model | **Pick + tune** — choose closest pack, retune `:root` values from the lesson's own nouns; textures/motifs fixed |
| 2 | Pipeline | **Parts folder + Python assembler** (`build.py`) with built-in mechanical validation |
| 3 | Library shape | **Folder-per-component + `registry.md` index**; unused components cost nothing; AI hand-writes only when registry has no fit |
| 4 | New components | **Propose → user approves** promotion into the library after a lesson build passes QA |
| 5 | Initial packs | 6 business-focused packs + hand-derive fallback (promotable to a 7th pack) |

## 3. Architecture

### 3.1 Skill directory

```
interactive-lesson-notebook/
  SKILL.md                    # rewritten (see §7)
  build.py                    # assembler + validator (Python 3 stdlib only)
  skeleton/
    shell.html                # layout + component CSS/JS + JS runtime, with markers
    themes/
      ledger.css              # :root values + .sheet texture + .decor motif + display voice
      receipt.css
      contract.css
      filecard.css
      boardmemo.css
      graph-paper.css
    components/
      registry.md             # discovery index (see §6.2)
      sort-statement/
      feasibility-gate/
      break-even-lab/         # sliders + SVG chart + plain-language readout + sensitivity table
      step-solver/
      true-false/
      ranked-statements/
      case-match/
      flipcards/              # recap
      milo-list/              # §0 click-to-tick outcomes with progress ring
      glossary/               # static lookup rendering
      comparison-table/
      # each folder: component.css, component.js, README.md
```

No `reference/notebook.html` — the skeleton is the source of truth. (v1.9 Part 7's phantom
reference file is retired.)

### 3.2 Shell markers

`shell.html` contains exactly these injection markers:

| Marker | Injected with |
|---|---|
| `__TITLE__` | title from build.json |
| `/*__THEME__*/` | chosen theme pack CSS verbatim |
| `/*__TUNE__*/` | `tune.css` (overrides block, applied after theme) |
| `/*__COMPONENT_CSS__*/` | CSS of selected components only |
| `<!--__SECTIONS__-->` | `sections.html` verbatim |
| `/*__DATA__*/` | `data.js` verbatim |
| `/*__COMPONENT_JS__*/` | JS of selected components only + init glue |

### 3.3 Mount pattern (standardization core)

- Components render themselves from data. In `sections.html` the AI writes only a mount:
  `<div data-component="sort-statement" data-key="week4sort"></div>`
- `data.js` assigns: `LN.data.week4sort = { left: 'Fixed cost', right: 'Variable cost', items: [...] };`
- Component JS registers into `LN.components['sort-statement'] = { init(root, data) {...} }`.
  Init glue (in shell) scans `[data-component]`, looks up `LN.components` + `LN.data[data-key]`,
  and errors loudly (visible red banner in the page) on unknown component or missing key.
- The sidebar TOC, scroll-spy, progress bar, and mobile drawer are shell-owned:
  auto-generated by scanning `section.block` headings. The AI never writes chrome.

## 4. Per-lesson build contract

The AI creates a workdir (default `build/<lesson-slug>/`) with four required files —
`build.json`, `tune.css`, `sections.html`, `data.js` — plus optional `extra.css` /
`extra.js`, and runs `python build.py <workdir>`:

| File | Contents | Target size |
|---|---|---|
| `build.json` | see schema below | ~10 lines |
| `tune.css` | `:root{ --tokens: overridden values only }` (10–25 lines) | small |
| `sections.html` | all teaching content: `section.block` bodies, `.def`/`.mini`/`.note`/prose, mounts | the real work |
| `data.js` | all component data arrays | content only |

`build.json` schema:

```json
{
  "title": "Week 4 — Feasibility Analysis",
  "theme": "receipt",
  "components": ["sort-statement", "break-even-lab", "true-false", "flipcards"],
  "output": "Week4-Notebook.html",
  "extra_css": "optional/extra.css",
  "extra_js": "optional/extra.js"
}
```

`extra_css` / `extra_js` exist so a lesson needing a not-yet-standard component still ships
through the pipeline (hand-written this lesson, proposed for promotion next).

Output: one self-contained `.html` written to `<workdir>/<output>`; `output` may be an
absolute path, otherwise it resolves inside the workdir. The assembled file is a
**read-only product** — fixes go to parts, then rebuild.

## 5. `build.py` responsibilities

### 5.1 Assemble

1. Parse `build.json`; verify referenced theme and components exist (unknown names → list valid options).
2. Read `shell.html`; substitute markers in order: theme → tune → component CSS → sections → data → component JS + init glue.
3. Refuse to write output unless every check below passes; exit code 1 + itemized report.

### 5.2 Validation (mechanical QA moved out of SKILL.md Part 5)

| Check | Rule |
|---|---|
| Marker hygiene | no `__X__` markers or `/*__` / `<!--__` left in output |
| Hex containment | no hex colour outside `/*__THEME__*/` + `/*__TUNE__*/` spans; component/section CSS must use `var(--token)` only |
| No external assets | grep for `http://`, `https://`, `@import`, `url(` with non-gradient argument |
| IDs | unique across assembled doc; every `section.block` has an id |
| Data integrity | every `[data-component]` mount's component is in the build list; every `data-key` is defined in `data.js` (static scan of assignments) |
| Well-formedness | HTML parse via `html.parser`; balanced tags |
| Contrast | compute WCAG ratios from final palette: ink vs surface/surface-2 ≥ 4.5:1; ink vs each section-tint composite ≥ 4.5:1; ink-faint vs grid ≥ 3:1; semantic hues stay in family (green/amber/red hue ranges) |
| Print block present | shell-owned, asserted by marker check |

Contrast math handles `#hex`, `rgb()`, and `hsl(… / a)` alpha compositing over the surface.

### 5.3 Failure UX

Every check prints: file, line where locatable, rule name, and fix hint. Exit 0 = written output.
The AI loop: run → fix parts → rerun until green. This is a hard gate: no output file on failure.

## 6. Component & theme library conventions

### 6.1 Component anatomy

- `component.css` — tokens-only colours, includes responsive/`prefers-reduced-motion` handling for itself.
- `component.js` — registers into `LN.components[name]`; renders from the data object; **zero content strings**; real `<button>`/`<input>` elements; one-way answer states where the pedagogy requires (§3.1/§3.6 rules of v1.9).
- `README.md` — purpose, full data-schema example, when-to-use / when-not.

### 6.2 `registry.md` format

One table: `teaching need → component → data schema (one line) → example mount`.
SKILL.md instructs: **read registry before writing any interactive element**; reuse if it fits.

### 6.3 Promotion flow (user-gated)

1. AI finishes a lesson build using `extra.css`/`extra_js` (or a hand-derived skin).
2. If it passed build validation + judgment QA, AI asks: *"Promote `<name>` to the library?"*
3. On approval only: create `components/<name>/` files + registry row (or `themes/<name>.css`), keeping data-schema identical.
4. On rejection: library untouched; the component still lives in that lesson's output.

No silent auto-adds. Duplicates are prevented by the registry-first rule.

### 6.4 Theme packs

Each pack = one `.css` file: filled `:root` token block + `.sheet` texture + `.decor` motif +
`--display` choice. Initial six (see §3.1) map to business domains:
ledger (accounting/finance), receipt (entrepreneurship/retail), contract (law/taxation),
filecard (HR/office admin), boardmemo (management/marketing strategy), graph-paper (economics/stats).

Tuning contract: `tune.css` may override **token values only** (colours, display stack, tracking) —
never structural rules. §1.4 semantic-hue lock (green/amber/red families) enforced by build.py.

## 8. Testing plan (writing-skills TDD)

**RED — baseline (before touching SKILL.md):**
1. Convert one real lesson with current v1.9 — the user supplies the source file
   (an unconverted week of the same course used so far).
2. Record: output token count, lines, every §5 QA failure found in the shipped file.

**Library verification:**
- `build.py` smoke tests: fixture workdir with known-bad inputs — hex in sections.css, left marker,
  unknown theme name, missing data-key, low-contrast tune — each must fail with the right rule named.
- One good fixture build per theme pack (6) and per component (mount renders, reset works — manual browser check of fixture output).

**GREEN:** convert the same lesson with v2.0 pipeline. Compare: output tokens (target ≤ 40% of
baseline), QA table pass/fail, opened-in-browser check.

**REFACTOR:** wherever the model fights the contract (marker confusion, schema gaps, packs that
all "blend" on real lessons), fix asset wording, re-test. Repeat with a second, non-business
lesson to verify the fallback derivation still works.

Deployment gate: SKILL.md v2.0 is only saved after GREEN passes. Work happens in a `v2/`
staging copy of the skill directory; live skill untouched until gate passes.

## 9. Error handling

- build.py: itemized report, exit 1, never writes partial output.
- Page runtime: unknown component/data-key shows a visible red banner (never silent blank region).
- Assembled output is read-only by convention; SKILL.md states it explicitly.
- If a lesson genuinely can't fit the pipeline (e.g., >40 pages per §2.3 split rule), old behavior
  applies: ask the user.

## 10. Out of scope

- New component types beyond the v1.9 Part 3 + §2.2 set (they arrive via promotion, not upfront design).
- Theme packs beyond the six (addable later as token files — cheap).
- Framework/CDN dependencies anywhere (still forbidden).
- Automated browser QA of interactivity (out of scope for v2.0; manual spot-check per lesson remains).

## 11. Success criteria

1. Same lesson converts with ≤ 40% of baseline output tokens.
2. All mechanical QA checks pass on first green build without model re-typing.
3. Two consecutive lessons using different packs + tuning are visually distinct; the packs alone are never shipped untuned twice.
4. The model can build a complete notebook while writing ≤ 4 files, never reading shell.html internals beyond the marker reference table.
